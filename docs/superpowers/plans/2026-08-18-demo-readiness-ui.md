# Demo Readiness UI — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give an operator four things ahead of a live demo: a bulk "turn on all" action, a clickable GitHub repo link, a free-text briefing field, and an operator-driven "scale for demo" control (ArgoCD replica count / ECS `desiredCount`) independent of the existing on/off restoration flow.

**Architecture:** Reuses the existing async job model (ADR-001). Three features (bulk turn-on, GitHub link, briefing) are frontend/schema-only. The fourth (scale) adds a new job `operation: 'scale'` with `targets` persisted on the job record, a new route guarded by a plain status read (check-then-act — `scale` has no status transition to attach a DynamoDB `ConditionExpression` to), and new controller-level methods on both `ArgocdController` (dispatching by workload kind) and `EcsController` — structurally separate from the existing turn_on/turn_off postlude so a scale job never mutates project on/off state. Revised across three rounds of cross-model plan review plus five rounds of this repo's own PR-review gate (2026-08-18); the round-2 review found the "live current-value pre-fill" feature architecturally unimplementable within the `api` package's thin-routes boundary, cut in the following revision. The first PR-review gate round fixed a remaining internal contradiction on the status-precondition mechanism, an inaccurate HPA-limitation description, and undefined behavior for the pre-existing zero-matched-workload-handles bug, and added an ADR task (Task 7). The second PR-review gate round established that the zero-matched-workload-handles bug means ArgoCD/HPA scaling is inert, unconditionally, until that pre-existing bug is fixed separately; added a worker-side status recheck at the start of the `scale` branch to shrink (not close) the `turn_off` race; and corrected the spec's own internal contradiction between its Known-limitations and Frontend-components sections on the scale-warning toast wording (settling on the spec's conditional phrasing). The third PR-review gate round found that this plan's own Task 6 Step 2 still quoted the pre-correction, unconditional wording that round's fix had settled on the opposite of — fixed here to match the spec exactly. The fourth PR-review gate round found the spec and this plan still disagreed on whether the `argocd-app` scale control ships enabled (settled on disabled, per Task 6 Step 4), corrected an overstated ADR claim about the cluster-wide ArgoCD `ignoreDifferences` fully protecting a `scale` patch (it doesn't survive a git-triggered sync without `RespectIgnoreDifferences=true`), and fixed a toast-scoping rule that could suppress the irreversibility warning exactly when a mixed-kind `argocd-app` target's HPA had already been mutated before a sibling handle failed. The fifth PR-review gate round fixed a count contradiction inside the ADR's own limitations enumeration (Task 7 said "five" while listing six), added the ADR-orphaned `dev-server.ts` to a concrete task (Task 5), reconciled a spec-vs-plan disagreement on whether the start-of-branch status recheck writes any per-target progress entries (it writes none — a job-level abort, not a per-target failure), and folded the in-flight-guard and `ignoreDifferences`/git-sync limitations into the ADR's enumeration so it's genuinely exhaustive rather than a superset of whatever happens to already be in the spec. See `docs/superpowers/specs/2026-08-18-demo-readiness-ui-design.md` for the full rationale — its Known limitations / Error handling sections cover most, but not all, of the accepted limitations; **Task 7's ADR is this feature's one complete, canonical enumeration**, and is the only place that should ever be treated as exhaustive.

**Tech Stack:** Backend — Node20 TS pnpm-workspace (Fastify, vitest, Node16 ESM `.js` imports). Frontend — Next.js 14 App Router, TS, **no test runner configured yet** (Task 0 adds one). Spec: `docs/superpowers/specs/2026-08-18-demo-readiness-ui-design.md`. Branch: `feat/demo-readiness-ui`.

**Deliverable units** → independent PRs, each green on its own: Task 0 (frontend test infra), Task 1 (GitHub link), Task 2 (briefing field), Task 3 (bulk turn-on, depends on Task 0's infra + the `toggle()` refactor inside it), Tasks 4–5 (scale action backend: job op+controllers → route), Task 7 (ADR + operator note — lands once Task 4 establishes the design's final shape, and must land before Task 6 per CLAUDE.md's auto-sync rules), Task 6 (scale action frontend UI, last).
